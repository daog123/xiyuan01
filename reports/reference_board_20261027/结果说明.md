## 这次定位到的问题

1. **加载后需要执行 system reset。** 先前仅观察配置完成，计算控制窗口仍不可用。本轮对照原参考 runner 的 `program → sys_reset → waitReady` 顺序，补上复位后，控制状态出现 ready/calibration 位，参考计算通过。
2. **计算存储访问采用先写后读。** 直接读取未初始化计算地址曾导致 DMA 超时；单卡恢复、加载后复位，再写入已知数据并读回成功。目前只将其作为实测有效的初始化顺序，不将具体底层原因认定为已查明。
3. **参考核拒绝小 K 配置。** K=32 和 K=64 均返回状态 0x36，包含协议/控制错误位。改为原基线已使用的 K=768，并补零保持数学结果不变，全部通过。尚未确认其完整 K 合法集合，因此不能声称“最小 K 是 768”。
4. **两种权重布局不同。** 项目按 N-major 打包 INT4；参考核使用 K-major、相邻输出列的低/高半字节打包。适配程序明确完成重排，并依据项目原参考模型的逐组部分和验收。

## 实际运行链路和边界

`项目输入与 INT4 打包 → 主机重排、按组补零 → FPGA 参考核计算 INT32 部分和 → 读回 → 主机按 sx/sw 合并 → Q16.16 舍入与饱和 → 项目参考结果核对`

- FPGA 上运行的是服务器既有 `phase1_matrix_engine_v1.bit`，不是 `E:/speed-up` 的 `w4a8_wave` 或 `llm_graph_top`。
- 主机执行尺度合并、输出舍入和饱和；这些步骤尚未通过本项目自研 RTL 在板上完成。
- K 补零、逐组发起任务用于正确性验证；本轮周期计数不能作为自研加速器性能、端到端时延或 tokens/s。
- 本轮没有修改 `E:/speed-up` 的 RTL，也未写入持久化 Flash。结束时选定卡保留已验证的参考矩阵配置，DMA 引擎空闲，四张卡仍可枚举；临时设备节点已清理，SSH 会话已关闭。

## 复现入口

将 `w4a8_reference_adapter` 目录放到该服务器，保留目录内的 C 源码、脚本和 data 输入。脚本要求上述固定 PCI、管理版本及 bitstream 校验和匹配，并检查卡是否被占用。

```bash
bash run_board_validation.sh --program-reference
```

该命令会对选定卡加载易失参考配置，暂存 bitstream 使用管理 DDR；会覆盖测试用 A/W/Y 缓冲区。它创建独立 run 目录并保存所有本轮输出，结束后清理自己的设备节点。若卡再次出现 DMA 超时，应先使用上一轮已验证的单卡恢复流程，再执行此脚本。

将新 run 的 `data/*.actual.bin` 和 `data/hardware_tasks.jsonl` 复制回本地适配目录的 `data` 后执行：

```powershell
python prepare_and_verify.py verify
```

本次保存的输入默认硬件 K=768。若需重新生成，用 `prepare` 模式；该模式需要本地项目参考模型且会重写输入清单。仅验收已保存结果用 `verify`，无需重新生成。
